# กระบวนการขายบูธ

จากผังที่ทีมเขียนไว้ ระบบเดินตามนี้ ไม่ใช่ตามที่ผมคิดเอง

    Sale A ─┐
    Sale B ─┼─> Event Floorplan Booking ─> Booking ─┬─> ใบเสนอราคา ─> Add on ─┐
    Sale C ─┘                                       │                        ├─> Confirm
                                                    ├────────────────────────┘
                                                    └─> Que 1 ─> Que 2 ─> Que 3,4,5

    Confirm ─> ใบวางบิล ─┬─> ใบกำกับ
                         ├─> Feasibility
                         └─> Exhibitor Sheetlist

## สิ่งที่ผังนี้บอก แล้วโครงเดิมยังไม่มี

### คิวรอบูธเดียวกัน

Que 1 / Que 2 / Que 3,4,5 คือคนที่อยากได้บูธเดียวกันแต่มาทีหลัง
วันนี้คิวอยู่ในหัวเซลล์ พอคนแรกไม่จ่ายมัดจำตามกำหนด ต้องนึกเองว่าโทรหาใครต่อ

ตาราง `booth_queue` เก็บ บูธ · ดีล · ลำดับ · สถานะ
พอบูธหลุดจากคนแรก ระบบบอกได้ทันทีว่าคิวถัดไปคือใคร เซลล์คนไหนดูแล

ข้อนี้สำคัญกับการตั้งราคาด้วย บูธที่มีคิวสามคนคือบูธที่ตั้งราคาต่ำไป
ซึ่งเป็นข้อมูลที่หายไปทั้งหมดในวิธีทำงานปัจจุบัน

### ลำดับเอกสารสามใบ

ใบเสนอราคา → ใบวางบิล → ใบกำกับ เป็นคนละใบและคนละเวลา
โครงเดิมมีแต่ `payment` ซึ่งเก็บ "เงินเข้าเมื่อไหร่" แต่ไม่ได้เก็บ "ออกใบอะไรไปแล้วบ้าง"

ตาราง `document` เก็บทั้งสามใบ พร้อมเลขที่ วันที่ ยอด และเลขอ้างอิงฝั่ง PEAK
หนึ่งใบวางบิลครอบได้หลายงวด จึงแยกจาก `payment` ไม่ยุบรวมกัน

### Add on อยู่ระหว่างใบเสนอราคากับ Confirm

ผังวางกล่อง Add on ต่อจากใบเสนอราคาแล้ววนกลับมา Confirm
ตรงกับตาราง `addon` และ `deal_item` ที่มีอยู่แล้ว
แปลว่าของขายเสริมถูกเสนอตอนต่อรอง ไม่ใช่ตอนปิดการขาย ซึ่งถูกแล้ว

### ปลายทางสองอันเป็นผลพลอยได้

Feasibility กับ Exhibitor Sheetlist คือสองชีตที่ทุกวันนี้ทีมกรอกมือ
ในผังมันคือปลายน้ำของใบวางบิล แปลว่าทั้งสองอันควรถูกสร้างจากข้อมูลเดียวกัน
ไม่ใช่ไฟล์ที่ต้องไปอัปเดตตามทีหลัง

`budget_line` กับมุมมองรายชื่อผู้ออกบูธจึงเป็นรายงาน ไม่ใช่ตารางที่ต้องกรอก

## สถานะของดีลตามคำที่ทีมใช้

    lead -> booking -> quoted -> confirmed -> billed -> paid
                          |
                          +-- lost / cancelled

ใช้คำเดียวกับที่เขียนในผัง เพื่อให้เซลล์อ่านหน้าจอแล้วตรงกับที่คุยกันในทีม

# หลังปิดการขาย — ดูแลผู้ออกบูธ

จากชีต Exhibitor Manual ที่ทีมใช้จริง 37 คอลัมน์ 239 แถว

## สิ่งที่ชีตติดตามอยู่ แบ่งได้สี่ระยะ

| ระยะ | ช่องในชีต |
|---|---|
| ตั้งต้น | ติดต่อหรือยัง · เข้ากลุ่ม Exhibitor · ส่ง Manual · แพคเกจ Ready to move |
| ของที่ต้องเก็บ | File LOGO · ชื่อหน้าคูหา · ป้ายหัวบูธ · บัตร Exhibitor · บัตร Contractor |
| เอกสาร | F6 คูหามาตรฐาน · F2 พื้นที่เปล่า · F3 แคชเชียร์เช็ค · เอกสารก่อสร้าง |
| ก่อสร้าง | ผนังคูหา · โครงพื้นที่เปล่า · Files แบบ · โครงสร้างบูธเพิ่มเติม |

ทำเป็นตาราง `task_template` กับ `exhibitor_task` แทนที่จะเป็นคอลัมน์ตายตัว
เพราะแต่ละงานใช้ฟอร์มไม่เหมือนกัน IMPACT กับ BITEC คนละชุด
และบูธพื้นที่เปล่ากับบูธโครงมาตรฐานต้องส่งคนละใบ

## เซลล์นอกกับเซลล์ใน ชีตแยกไว้แล้ว

ในชีตมีทั้ง จ๋อมแจ๋ม · สนุ๊ก · พี่นก (คนใน)
Talk Event · Anster · พี่แคท (Sale Agent)
และ Torpenguin (ส่วนกลาง) ซึ่งคือบูธที่บริษัทให้ฟรีหรือถือเอง

สามอย่างนี้คิดค่าคอมคนละแบบ และงบตั้ง Sales Agent Commission ไว้ 10–15%
ตาราง `sales_agent` กับ `deal.agent_id` ทำให้คิดค่าคอมจากดีลจริงได้
แทนการคูณยอดรวมทั้งงานด้วยเปอร์เซ็นต์เดียว

## เงื่อนไขบูธอยู่ในช่อง Remark

ตัวอย่างที่เจอ — "Standard ไม่เอาโครง เอาพรม เอาเฟอร์นิเจอร์ เอาปลั๊ก ไม่ได้ไฟ" ·
"เปิดผนังเชื่อมกับบูธ A34" · "ย้ายตำแหน่งจาก A36" · "Torpenguin ให้บูธฟรี"

พวกนี้คือเงื่อนไขที่ทีมก่อสร้างต้องรู้ แต่วันนี้อยู่ในช่องข้อความยาว ๆ ที่ค้นไม่ได้
`move_in.wall_note` กับ `deal.conditions` แยกสองเรื่องนี้ออกจากกัน

**ข้อควรระวัง** ชีตนี้คอลัมน์เลื่อนในหลายแถว เพราะช่องว่างถูกตัดตอน export
ตัวเลขสรุปที่ผมนับได้จึงเป็นตัวประมาณ ไม่ควรเอาไปใช้ตัดสินใจโดยไม่เปิดชีตดูซ้ำ
