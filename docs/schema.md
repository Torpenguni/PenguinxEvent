## 1. เรื่องที่พบแล้วเปลี่ยนวิธีออกแบบ

### ส่วนลดจริงไม่เท่ากันสักชั้น แต่ชีตใช้ตัวเลขเดียว

ชีต Feasibility ตั้งราคาไว้ แล้วหักด้วยบรรทัดเดียวว่า `Discounts 40%`
พอเอาราคาที่ขายได้จริงรายดีลมารวมกัน ภาพเป็นคนละเรื่อง

| ชั้น | จำนวนดีล | ราคาตั้งรวม | ขายได้จริง | ส่วนลดจริง |
|---|---:|---:|---:|---:|
| Title | 2 | 3,000,000 | 3,000,000 | 0% |
| Platinum | 5 | 3,500,000 | 1,800,000 | 49% |
| Gold | 16 | 6,400,000 | 2,970,000 | 54% |
| Silver | 17 | 3,400,000 | 2,625,000 | 23% |
| Standard A | 36 | 1,800,000 | 995,000 | 45% |
| Standard B–D | 35 | 1,750,000 | 1,293,500 | 26% |
| **รวม** | **111** | **19,850,000** | **12,683,500** | **36%** |

Title ขายเต็มราคา Gold ลดครึ่ง Silver ลดแค่ยี่สิบกว่า
ใช้ 40% ก้อนเดียวมองไม่เห็นว่า **Gold คือชั้นที่ราคาพัง** ทั้งที่ตั้งราคาสูงสุดรองจาก Platinum

ระบบจึงเก็บ `list_total` กับ `deal_total` แยกกันในตาราง `deal`
และเก็บ `list_unit_price` คู่กับ `unit_price` ในทุกบรรทัดของ `deal_item`
ส่วนลดเป็นผลลัพธ์ที่คำนวณได้ ไม่ใช่ตัวเลขที่ต้องเดาตอนตั้งงบ

### บูธที่แจกฟรีปนอยู่ในตัวเลขส่วนลด

18 จาก 111 ดีล ราคา 0 บาท — RBA, RMBA, Thai Franchise Center, Jagota, Expert Printing
พวกนี้ไม่ใช่ "ลด 100%" แต่คือแลกของ แลกสื่อ หรือพันธมิตรที่ต้องมีในงาน
ถ้านับรวมเป็นส่วนลด ตัวเลขส่วนลดจะบวมโดยไม่มีความหมาย

`deal.settlement` จึงแยก `cash` / `barter` / `free` / `partial_barter`
รายงานส่วนลดคิดเฉพาะ `cash` ส่วน barter บันทึกมูลค่าที่ตีไว้ใน `barter_note`

### สถานะบูธถูกเก็บเป็นสีเซลล์

ในชีต Damn Expo มีโน้ตเขียนไว้ว่า *"สีเขียวคือว่าจะแจกฟรี แต่ถ้าลูกค้าจะซื้อก็ซื้อได้"*
แปลว่าสถานะสำคัญที่สุดของบูธอยู่ในสีพื้นหลัง ซึ่งค้นไม่ได้ นับไม่ได้ และหายเวลา copy ชีต

`booth.status` จึงเป็นคอลัมน์จริง `available / held / contracted / deposit_paid / paid / blocked`
สีบนผังเป็นผลจากสถานะ ไม่ใช่ที่เก็บสถานะ

### ผังวาดด้วยการ merge ช่องตาราง

ทั้งสองไฟล์ผังคือกริดที่ merge ช่องแล้วพิมพ์ `A11 ล่าเมียว` ลงไป
วิธีคิดนี้ดีอยู่แล้วและทีมคุ้นมือ ระบบเลยเก็บพิกัดเป็น `grid_x, grid_y, grid_w, grid_h`
วาด SVG จากกริดตรง ๆ ไม่ต้องมีตัวลากวางที่ใช้ยากกว่าเดิม

รหัสบูธที่พบ ใช้อักษรนำเป็นโซน แล้วต่อด้วยเลขรัน
TRC ใช้ A E F H N X · Damn Expo ใช้ A B D F N บวก T P G S ของสปอนเซอร์
`zone.code` กับ `booth.code` รับรูปแบบนี้ได้เลย

### ผังมีหลายรุ่น และคนละรุ่นคนละเจ้าของ

ในไฟล์เดียว บูธ D6 ปรากฏเป็น Mr. Big, Mt.Big, ซ้งซอสหม่าล่า และ Bar Tools
คือแท็บคนละรอบแก้ ไม่มีใครรู้ว่ารุ่นไหนจริง

`audit_log` จึงบันทึกทุกการเปลี่ยนสถานะและเจ้าของบูธ พร้อมคนทำและเวลา
ทีม 15–20 คนแก้ผังเดียวกัน ข้อนี้ไม่ใช่ของแถม

### หนึ่งฮอลล์มีสองงาน

ชีตงบแยกทุกบรรทัดเป็น `(Restech)` กับ `(ตั้งตัว)` ตั้งแต่ราคาบูธยันค่าเวที
และบรรทัด Sub total แยกยอดสองงานออกจากกัน

`event_brand` รองรับข้อนี้ โซน บูธ ดีล และบรรทัดงบ ผูกแบรนด์ได้
ผังยังเป็นผังเดียว แต่ยอดขายและงบแยกกันได้จริง

### ของขายเสริมมีอยู่แล้ว แค่ยังไม่มีใครขาย

ในชีตมี Additional MC On Ground 2,000 · ภาพนิ่งบูธ 500 · ภาพวิดีโอบูธ 5,000 ·
Additional Speaker Session 120,000 — ทุกบรรทัดจำนวนเป็น 0

ตาราง `addon` กับ `deal_item` แยกของพวกนี้ออกจากค่าบูธ
พอมันโผล่บนหน้าจอตอนปิดดีล เซลล์จะเห็นว่ามีให้ขาย

### ต้นทุนต่อบูธคำนวณได้

ฝั่งรายจ่ายมี Shell Scheme 3x3 ที่ 2,500 · 2x2 ที่ 1,800 · ปูพรม 45–50 ต่อตารางเมตร ·
กระแสไฟบูธ 750 ต่อบูธ

`booth_type.build_cost` เก็บตัวนี้ไว้ พอมีทั้งราคาขายจริงและต้นทุน
ระบบตอบได้ว่าบูธไหนขายแล้วขาดทุน — คำถามที่ชีตตอบไม่ได้เลยทุกวันนี้

### ค่าคอมมิชชั่นผูกกับยอดที่ปิดได้

ชีตคิด Sales Agent Commission 10–15% ของรายได้รวมเป็นก้อนเดียว
`deal.owner_id` กับ `deal.commission_rate` ทำให้คิดรายคนรายดีลได้
และได้กระดานยอดเซลล์มาฟรีจากข้อมูลชุดเดิม

## 2. เชื่อมกับ PEAK

PEAK มี REST API เปิดให้ใช้ ต้องแพ็กเกจ PRO Plus ขึ้นไป (12,000 บาทต่อปี)
endpoint ที่มีตรงกับขั้นตอนขายของเราพอดี

| ขั้นในระบบเรา | endpoint ฝั่ง PEAK |
|---|---|
| ลูกค้าใหม่ | `POST /api/v1/contacts` |
| เสนอราคา | `POST /api/v1/quotations-allinone` |
| ปิดดีล ออกใบแจ้งหนี้ | `POST /api/v1/invoices-allinone` |
| รับมัดจำ | `POST /api/v1/invoices-paidpayment` |
| ออกใบเสร็จ | `POST /api/v1/receipts-allinone` |

เก็บ id ที่ PEAK คืนมาไว้ใน `deal.peak_quotation_id`, `deal.peak_invoice_id`,
`payment.peak_receipt_id` เพื่อไม่ให้ยิงซ้ำและตามเอกสารกลับได้

**ทิศทางที่ควรเป็น** ระบบนี้เป็นต้นทาง PEAK เป็นปลายทาง
เราไม่ดึงตัวเลขจาก PEAK มาแสดง เพราะจะได้ระบบสองระบบที่เถียงกันเอง

**เฟสแรกยังไม่ต้องเชื่อม** ทำช่องเก็บ id ไว้ก่อน แล้วให้กดออกเอกสารเองไปพลาง
ค่อยต่อ API ตอนที่ flow ขายนิ่งแล้ว ไม่งั้นแก้ flow ทีต้องแก้ integration ตาม

## 3. ขนาดที่ต้องรองรับ

100–300 บูธ 5–6 โซนต่องาน · 4 งานใหญ่ 5–6 งานย่อย · ผู้ใช้ 15–20 คน

เล็กมากสำหรับ PostgreSQL ผังทั้งงานโหลดทีเดียวได้สบาย ไม่ต้องแบ่งหน้า
ข้อจำกัดจริงคือคนแก้พร้อมกัน ไม่ใช่ปริมาณข้อมูล
