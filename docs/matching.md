# Business matching ของ hosted buyer program

งานส่วนใหญ่ที่เราจัดคือบูธจากต่างประเทศมาหาผู้ซื้อไทย คุณค่าที่เราขายได้จริงจึงไม่ใช่พื้นที่
แต่คือ "เจอคนที่ซื้อได้กี่ราย" โมดูลนี้ทำให้สิ่งนั้นวัดได้และทำซ้ำได้

## ขอบเขตเฟสแรก

ทีมเป็นคนจัดทั้งหมด ไม่เปิดให้ผู้ซื้อหรือผู้ออกบูธเข้ามากดเอง
ความต้องการว่าใครอยากเจอใครมาจากโทรศัพท์ ไลน์ และอีเมล แล้วทีมคีย์เข้าระบบ
สิ่งที่ระบบต้องทำคือรับข้อมูลนั้นไปจัดตารางที่ไม่ชนกัน แล้วพิมพ์ออกมาให้ทุกคนถือเดินได้

การตัดสินใจสามข้อที่กำหนดโครงสร้าง

- **นัดเกิดได้ทั้งสองแบบ** บูธใหญ่ให้นัดที่บูธตัวเอง บูธเล็กใช้โต๊ะเจรจากลางที่มีจำนวนจำกัด
- **ทีมคีย์ความต้องการเองทั้งหมด** ยังไม่มีหน้าจอสำหรับคนนอก
- **สิทธิประโยชน์ออกตอนยืนยัน แล้วตัดทีหลังถ้าไม่มาจริง**

## ของที่มีอยู่แล้ว ไม่ต้องทำใหม่

ตาราง `buyer` (`db/buyer.sql`) เก็บทะเบียนผู้ซื้อที่คัดแล้ว พร้อมสถานะหกขั้น
`applied → qualified → invited → confirmed → attended` และ `declined`

คะแนนคัดกรองสี่ด้าน (`bscore` ใน `prototypes/mock_js.txt`) คำนวณสดจากตำแหน่ง จุดประสงค์
จำนวนสาขา และช่วงงบ ทุกคะแนนอธิบายได้ว่ามาจากอะไร โมดูลนี้ใช้คะแนนเดิมต่อ ไม่สร้างเกณฑ์ใหม่

**หมวดสินค้าเป็นคำศัพท์ชุดเดียวกันอยู่แล้ว** ผู้ซื้อเลือก `interests` จากชื่อโซนของงาน (`buyerCats()`)
และบูธที่ดีลถืออยู่ก็ผูกกับ `zone` เดียวกัน การจับคู่หมวดจึงเทียบกันได้ตรง ๆ ไม่ต้องทำตารางแปลง

## ตารางใหม่

ไฟล์ `db/match.sql` เขียนแบบรันซ้ำได้เหมือนโมดูลอื่น และต้องผนวกเข้า `db/schema.sql` ด้วย
เพราะ `Procfile` ตอน release รันแค่ `schema.sql` กับ `seed.sql` ไฟล์แยกจะไม่ถูกรันบนเซิร์ฟเวอร์

| ตาราง | เก็บอะไร |
|---|---|
| `meeting_slot` | ช่วงเวลานัดของงาน วัน เวลาเริ่ม ความยาว ชนิด (`meeting` หรือ `break`) |
| `meeting_place` | ที่นัด `kind` เป็น `table` (โต๊ะกลาง) หรือ `booth` (เก็บ `booth_code`) พร้อมจำนวนที่นั่ง |
| `match_pref` | ใครอยากเจอใคร `side` buyer/exhibitor · `weight` must/nice/exclude · ใครคีย์ |
| `meeting` | นัดหนึ่งครั้ง ผูก `buyer_id` ชื่อบริษัท `slot_id` `place_id` สถานะ คะแนน และเหตุผลที่จับคู่ |
| `perk_rule` | กฎสิทธิประโยชน์ ชนิด เงื่อนไข จำนวน ต้นทุนต่อหน่วย โควตารวม |
| `buyer_perk` | สิทธิ์ที่ออกให้รายคน `entitled → issued → redeemed` หรือ `revoked` พร้อมเหตุผล |

**ห้ามเก็บไว้ในก้อน event** การบันทึกทั้งงาน (`PUT /api/events/:id/full`) ลบแถวของงานแล้วเขียนใหม่
ตารางนัดจะหายทุกครั้งที่มีคนขยับบูธ ด้วยเหตุผลเดียวกับที่ `buyer` แยกออกมาตั้งแต่แรก
ผูกกลับด้วย `code` ของงานเหมือนกัน และฝั่งผู้ออกบูธอ้างด้วยชื่อบริษัท ไม่ใช่ `deal_id`
ซึ่งได้ id ใหม่ทุกครั้งที่บันทึก เป็นวิธีเดียวกับที่ `deal_stage_log` ใช้อยู่แล้ว

## ตัวจับคู่

คะแนนต้องอธิบายได้ทุกนัด ไม่ใช่กล่องดำ ทุกแถวเก็บ `reason` ไว้ว่าเข้าคู่เพราะอะไร
เวลาผู้ออกบูธถามว่าทำไมได้เจอคนนี้ ต้องตอบได้ทันทีโดยไม่ต้องเปิดโค้ด

```
must ฝั่งใดฝั่งหนึ่ง        +100     exclude ฝั่งใดฝั่งหนึ่ง   ตัดทิ้ง
nice ฝั่งใดฝั่งหนึ่ง         +40     หมวดสินค้าตรงกัน        +30
คะแนนผู้ซื้อ (bscore)     +0..20     แพ็กเกจระดับสูงของดีล    +10
```

ข้อจำกัดตอนวางลงช่วงเวลา

- คนเดียวกันอยู่สองที่พร้อมกันไม่ได้ ทั้งฝั่งผู้ซื้อและฝั่งพนักงานประจำบูธ
- เพดานนัดต่อผู้ซื้อหนึ่งคน ตั้งได้ต่องาน ตั้งต้นที่ 6–10 นัด
- โต๊ะกลางมีจำนวนจำกัด ใช้เกินจำนวนโต๊ะในช่วงเวลาเดียวกันไม่ได้
- **นัดที่บูธต้องเว้นเวลาเดิน** ถ้านัดติดกันอยู่คนละโซน ต้องเว้นหนึ่งช่วง ข้อนี้มีเฉพาะโหมดผสม
- ไม่ให้ผู้ซื้อคนเดียวเจอหมวดเดียวกันติดกันเกินสองเจ้า คนซื้อจะจำไม่ได้ว่าใครเป็นใคร

วิธีจัดคือเรียงคู่ตามคะแนนแล้ววางจากมากไปน้อย ไม่ต้องใช้อัลกอริทึมหาค่าเหมาะที่สุด
เพราะทีมจะปรับมือทีหลังอยู่ดี สิ่งที่สำคัญกว่าคือ **นัดที่ปรับมือแล้วต้องถูกล็อก**
กด generate รอบใหม่แล้วของที่ล็อกไว้ต้องไม่ถูกทับ ไม่งั้นไม่มีใครกล้ากดปุ่มนั้นอีก

## หน้าจอ

แท็บใหม่ใต้เมนู Buyer ที่มีอยู่แล้ว

1. **Setup** ช่วงเวลา โต๊ะ บูธที่เข้าร่วม เพดานนัดต่อคน
2. **Preferences** ทีมคีย์ must / nice / exclude ทั้งสองฝั่ง — หน้านี้คือคอขวดจริง
   ผู้ซื้อ 200 คน คนละ 10 รายการ คือ 2,000 แถวที่ต้องคีย์ ต้องพิมพ์ชื่อแล้วเลือกได้เลย
   ใช้คีย์บอร์ดล้วนจบทั้งแถว ถ้าต้องจับเมาส์ทุกแถว ทีมจะกลับไปใช้ Excel ภายในวันเดียว
3. **Generate & review** กริดช่วงเวลา × ที่นัด ปรับมือได้ ล็อกได้ ธงบอกที่ยังชนหรือยังว่าง
4. **Publish & export** ตารางรายคนทั้งสองฝั่ง ออกเป็นไฟล์และสั่งพิมพ์ได้ เฟสนี้ส่งเองทางไลน์
5. **On-site** เช็กอินรายนัด มาจริง หรือไม่มา ใช้บนแท็บเล็ตที่จุดลงทะเบียน
6. **Perks** สิทธิ์ที่ออกแล้ว ใช้แล้ว ถูกตัด และต้นทุนรวม
7. **Analytics** นัดต่อคน อัตรามาจริง หมวดที่ผู้ซื้อขอแต่ไม่มีบูธรองรับ

## สิทธิประโยชน์

ออกตอนผู้ซื้อยืนยัน เพื่อให้เขาเห็นของก่อนตัดสินใจเดินทาง แล้วค่อยตัดถ้าไม่มาจริง

```
นัดยืนยันครบ 6 ขึ้นไป                      → บัตรอาหาร 2 ใบ
จังหวัดนอก กทม. ปริมณฑล และนัดครบ 8 ขึ้นไป  → ที่พัก 1 คืน
```

เกณฑ์เก็บเป็นข้อมูลใน `perk_rule` ไม่ฝังในโค้ด ด้วยเหตุผลเดียวกับตารางสิทธิ์ใน `access.md`
ทุกใบมีรหัสสั้นให้ร้านหรือโรงแรมกาเวลาใช้ และมีต้นทุนต่อหน่วยที่ไหลเข้า `budget_line`
หมวด hosted buyer ทันทีที่ออกใบ ต้นทุนโปรแกรมจึงโผล่ใน P&L โดยไม่ต้องรอปิดงาน

หลังงาน คนที่เช็กอินจริงต่ำกว่าเกณฑ์จะถูกตั้งเป็น `revoked` พร้อมเหตุผล
ไม่ใช่เพื่อทวงของคืน แต่เพื่อให้ปีหน้ารู้ว่าใครรับสิทธิ์แล้วไม่มา

## สิทธิ์การเข้าถึง

เพิ่มโมดูล `match` ใน `role_permission` ไม่ยืมสิทธิ์ `deal` ที่ `buyer` ใช้อยู่
เพราะคนคุมตารางนัดกับคนขายบูธเป็นคนละหน้าที่ ตั้งต้น ปฏิบัติการ `write` เซลล์ `read`
ผู้บริหาร `read` แอดมิน `write`

## ยังไม่ทำในเฟสนี้

- ให้ผู้ซื้อเลือกเองผ่านลิงก์ กลไกพร้อมแล้วใน `portal_access` ลิงก์แบบไม่มีรหัสผ่านที่ทำไว้ให้ผู้ออกบูธ
  ใช้ซ้ำได้ทั้งชุด เปลี่ยนแค่ว่าอีกฝั่งเห็นอะไร
- เลื่อนนัดเองและปฏิเสธนัดเอง
- อีเมลยืนยันและอีเมลเตือนอัตโนมัติ ต้องตั้ง `RESEND_API_KEY` บนเซิร์ฟเวอร์ก่อน
- เช็กอินด้วย QR ของผู้ซื้อเอง เฟสนี้เจ้าหน้าที่กดให้

## สถานะตอนนี้

ขั้นที่ 1 ลงแล้ว ตารางทั้งหกอยู่บนฐานข้อมูลจริง และมีสามหน้าจอใต้เมนู Buyer

| เส้นทาง | ใช้ทำอะไร |
|---|---|
| `GET /api/events/:code/match` | อ่านทั้งโมดูลในคำขอเดียว |
| `PUT /api/events/:code/match/slots` · `/places` | ตั้งช่วงเวลาและที่นัด เขียนทับตามคีย์ธรรมชาติ ไม่ลบแล้วสร้างใหม่ |
| `POST /api/events/:code/match/prefs` · `PATCH` `DELETE /api/match/prefs/:id` | คีย์ว่าใครอยากเจอใคร ทีละรายการ |
| `POST /api/events/:code/match/meetings` · `PATCH` `DELETE /api/match/meetings/:id` | นัดรายครั้ง ตัวจับคู่ในขั้นถัดไปจะเรียกเส้นนี้ ไม่มีทางเขียนที่สอง |
| `PUT /api/events/:code/match/rules` | กฎสิทธิประโยชน์ แก้ได้ในหน้าจอ ไม่มีเกณฑ์ไหนอยู่ในโค้ด |
| `GET /api/events/:code/match/perk-preview` | ถ้าใช้เกณฑ์นี้จะออกไปกี่ใบ ให้ใคร เป็นเงินเท่าไหร่ คำนวณสด ไม่เขียนอะไรลง |

การชนกันกันที่ฐานข้อมูล ไม่ใช่ที่หน้าจอ ที่นัดหนึ่งที่รับได้หนึ่งนัดต่อหนึ่งช่วงเวลา
และผู้ซื้อหนึ่งคนอยู่สองที่พร้อมกันไม่ได้ เป็น unique index สองตัวบนตาราง `meeting`
ตัวจับคู่อัตโนมัติกับการลากปรับมือเขียนคนละทาง ถ้ากันแค่ฝั่งหน้าจอจะมีวันที่ตารางชนกันจริง

## ลำดับการทำ

| ขั้น | ได้อะไร |
|---|---|
| 1 | ตาราง + endpoint + หน้า Setup และ Preferences — คีย์ข้อมูลเข้าได้ครบ |
| 2 | ตัวจับคู่ + กริดปรับมือ + ออกตารางรายคน — ใช้จัดงานจริงได้แล้ว |
| 3 | เช็กอิน + สิทธิประโยชน์ + ต้นทุนเข้างบ + สถิติ |

ขั้น 1 กับ 2 ต้องเสร็จพร้อมกันถึงจะมีประโยชน์ ขั้น 3 ตามทีหลังได้โดยไม่กระทบของเดิม
